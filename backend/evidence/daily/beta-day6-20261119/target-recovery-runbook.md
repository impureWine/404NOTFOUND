# 目标 PostgreSQL 迁移与恢复操作清单（待执行）

2026-11-19，庄剀涵。当前没有约定测试库、PostgreSQL 客户端或独立删除日志服务；以下是交接步骤，**当天未执行**。

1. 冻结源码完整 SHA、构建包、目标 PostgreSQL 版本、源库和独立恢复库标识。确认恢复库无业务流量，使用独立受限账号；凭据放在本机受保护的 pgpass/服务配置或秘密管理中，不写入命令日志、报告或仓库。核对库标识后才允许写操作。
2. 核对数据库权限、扩展、备份加密工具、磁盘空间及密钥恢复路径。目标建议按团队原定 PostgreSQL 16 验证；pg_dump 不得旧于源服务端主版本，pg_restore 与备份格式版本匹配。记录真实版本，不凭客户端存在性判为通过。
3. 将源库备份保存到受限且加密的存储位置，验证备份和密钥可读取。参考命令（服务名/路径须由运维实际配置）：`pg_dump --dbname="service=beta_source" --format=custom --file=<受限加密卷中的备份路径>`。custom 格式本身不加密。记录时间、SHA-256、备份范围及工具版本；不上传备份文件。
4. 在仅供演练的目标库设置 backend 本机 DATABASE_URL 后显式执行 `node src/db/migrate.js`。首次与再次执行分别记录迁移名称和结果。当前共7份：001基线、002、003、004_auth、004_identity、005、006；重复执行应零新增。不得修改已运行 SQL 的校验和来绕过错误。确认应用版本与005可选情绪字段、006来源快照兼容。
5. 在另一个空的、隔离的恢复库导入备份，参考 `pg_restore --dbname="service=beta_restore" --exit-on-error --single-transaction --no-owner --no-acl <备份路径>`。提前准备被引用的角色/扩展；不要使用 `--clean` 对现有业务库操作。失败立即保持离线，记录原因。使用单独的后端配置在恢复库校验迁移，禁止让迁移命令仍连接源库。
6. 依据备份时点到恢复截止时点的独立删除日志，核对序列连续性、来源可信性、保留期并实际重放删除。团队既有策略为业务备份7天、独立删除日志至少8天，运维需确认覆盖整个恢复窗口。专门演练“备份后清除、恢复旧备份”场景：被清除记录在开放前必须不可读取。当前仓库没有完整的独立日志读取/重放实现，不能用确认布尔值代替。
7. 重放证据确认后调用现有 `secureRestoredDatabase`，传入布尔 `true`，撤销全部旧会话，记录撤销数量和待发布 outbox 数量。通过实际下游机制处理 outbox 并核对状态，不能直接把 published_at 改成非空当作成功。校验账号/入口隔离、加密正文、日期、查询来源和幂等重试；错误密钥须拒绝、旧会话须失效。备份前后清除场景均需留证。
