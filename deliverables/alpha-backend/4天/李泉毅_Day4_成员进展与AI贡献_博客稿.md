## 从昨日站立式会议至今的进展

今天完成记录保存、读取、隔离和两步清除的后端纵向链。记录归属由服务端认证会话中的 `accountId + entryPointId` 决定，客户端提交的账号或入口字段不能改变作用域。保存接口要求有效的 `SAVE / RECORD_CREATE` 用途许可，并将许可绑定到具体记录类型和内容载荷。

记录创建和清除均使用 `requestId` 保证幂等。创建时的幂等摘要改为基于加密前业务载荷计算，解决 AES-256-GCM 每次生成随机密文后，同一请求重放被误判为载荷变化的问题。并发修改和清除使用 `expectedVersion` 做乐观锁校验；清除前还需要两分钟内有效的一次性确认，成功后在事务中清理正文、软删除主记录并写入 deletion outbox。

我补充了列表查询和清除确认的共享严格契约。列表只接受 `kind`、`limit`、`cursor`，非法范围或未知参数返回 400；清除确认必须携带版本号，未知字段返回 400，过期版本返回 409。新增 HTTP 集成测试覆盖创建与清除的幂等重放、跨入口隔离、退出后旧会话失效以及上述负向场景。合并 GitHub 最新 `main` 后，后端完整回归为 90/90 通过。

## 存在的问题与遇到的困难

1. 本机命令行连接 GitHub 时持续出现连接重置或 443 端口不可达，因此只能先通过已登录浏览器核对 `main` 的新提交；本地远端引用尚未同步。
2. 自动化使用 PGlite，不等同于正式 PostgreSQL 16。事务、约束和 SQL 行为仍需在正式数据库环境复核。
3. HTTP 创建链当前只开放 `CONVERSATION`，其他记录类型虽有仓储能力，但不能写成业务 API 已全部开放。
4. 前端网络面板、浏览器存储、改密后的跨页面行为以及非作者复测尚未完成，不能用自动化结果替代人工联调。

## 今日心得

幂等不能只看 requestId，也不能拿随机加密后的字节直接代表业务载荷。稳定摘要应基于规范化的明文业务结构计算，而数据库仍只保存密文。记录隔离也不能依赖前端传参，必须从服务端会话推导账号和入口，并用负向测试确认伪造参数没有绕过路径。
