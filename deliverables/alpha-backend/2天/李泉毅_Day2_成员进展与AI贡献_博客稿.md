## 从昨日站立式会议至今的进展

今天在 Day 1 接口骨架基础上完成了认证与个人资料的后端纵向链，并先同步团队 GitHub 更新，将数据工程成员新增的迁移、仓储、账号与入口隔离能力整合到现有 `backend/`，避免另建一套数据库实现。

认证部分已实现注册、登录、退出和修改密码。密码通过 Argon2id 生成摘要，参数为 19 MiB 内存、time cost 2、parallelism 1；数据库中不保存明文密码。登录使用随机令牌，服务端只保存 SHA-256 摘要。写请求要求当前会话、同源 Origin 与 CSRF token；Cookie 使用 HttpOnly 和 SameSite=Lax，本机 HTTP 开发使用普通 `session` 名称，HTTPS 配置下使用带 Secure 的 `__Host-session`。

资料部分已实现登录后读取和修改，使用版本号做乐观锁，避免旧页面覆盖新资料；个人简介以 AES-256-GCM 加密后保存。修改密码会验证当前密码、更新 Argon2id 摘要，并撤销该账号已有会话，使旧会话和旧密码失效。

我还补充了用途许可和记录链路的基础验证：许可按所有者、用途、操作、五分钟有效期、撤销状态和具体业务载荷摘要绑定，防止把一次许可挪作其他内容；记录接口验证了账号隔离、密文落库与两步清除。这部分为 Day 4 提前准备，不将其冒充为已完成前端联调。

截至本次记录，合并 GitHub 最新前端提交后，后端执行 `pnpm test` 共 31 项通过、0 失败、0 取消，约 7.02 秒。前端新增的 API 适配器测试 5/5 通过，Vite 构建通过，但页面仍默认使用 mock，因此只能说明适配器可测试、可构建，不能说明注册登录页面已经真实联调。

## 存在的问题与遇到的困难

1. 自动化数据库环境为 PGlite，可验证迁移和主要 SQL 行为，但不能替代正式 PostgreSQL 16 的网络、角色、备份、性能和部署验收。
2. 资料更新时，同一 SQL 参数同时用于 `bytea` 写入和空值判断，曾触发 `42P08` 参数类型不明确；通过显式转换为 `$5::bytea` 修复，并已加入回归覆盖。
3. 用途许可的初版只绑定用途和操作，仍可能被同一用户换载荷复用；现已增加稳定 SHA-256 载荷摘要绑定并补充错误载荷 403 测试。
4. 当前前端适配器与后端大部分路由已经对齐，但页面仍是模拟数据，真实浏览器 Cookie、CSRF 和退出后界面清理尚待前端共同联调。
5. 当前环境对 Wikipedia 的一次实网查询返回 `SERVICE_UNAVAILABLE`，所以没有记录成真实检索成功；这属于 Day 3 待复核事项。

## 从现在到下一次站立式会议的安排

1. 与前端工程师按注册→登录→查看资料→退出路径进行真实联调，核对字段、Cookie、CSRF 和错误状态。
2. 完善会话状态、查询任务状态、主动取消、会话结束和迟到响应失效处理。
3. 复核改密后所有旧会话失效，并补账号切换和其他所有者访问拒绝场景。
4. 在可用网络环境重试真实 Wikipedia 查询，分别记录成功、空结果、超时和不可用状态，不用替身结果冒充实网成功。
5. 每次开始工作前重新 fetch GitHub；如有团队更新，记录新增提交、受影响文件和回归结果。

## 今日心得

认证功能不能只看“能够登录”。密码摘要、会话令牌、Cookie、CSRF、资料加密、改密撤销和账号隔离必须作为一条完整链路验证。今天的两处缺陷都是在补充负向测试后暴露出来的，这说明自动化测试不仅用于证明成功路径，也用于迫使实现满足最初设计的安全边界。
