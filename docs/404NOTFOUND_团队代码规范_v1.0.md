### 1.3 约束等级与裁剪原则

- **必须**：合并前满足；确有例外时，在 PR 中说明规则编号、原因、替代措施、责任人和到期条件，由模块负责人及非作者评审记录结论。
- **建议**：通常采用；不采用时说明合理原因。
- **参考**：按场景选择，不作为独立阻断条件。

用户明确指令及项目既有业务、隐私和接口约束优先于一般风格建议。格式冲突以团队已采纳的仓库配置为准；配置与本文不一致时，用单独 PR 同步修订。禁止借格式化混入业务变更。

语言规则分别处理：Java 的 Bean 布尔命名、受检异常、包结构和四空格示例不直接套用到 JavaScript。本文采用 `isLoading`、`hasPermission` 等 JS 布尔命名和二空格缩进，属于有意裁剪。

## 2. 命名约定（NAM）

| 编号 | 对象 | 必须采用的约定 | 示例 |
| --- | --- | --- | --- |
| NAM-01 | 变量、参数、函数、对象属性 | lowerCamelCase；准确英文，业务含义明确 | `recordId`、`saveRecord` |
| NAM-02 | React 组件、类 | PascalCase；组件文件与主要组件同名 | `RecordCard.jsx`、`AppError` |
| NAM-03 | 共享固定常量 | UPPER_SNAKE_CASE；说明业务含义及单位 | `MODEL_TIMEOUT_MS` |
| NAM-04 | 布尔值 | `is`、`has`、`can`、`should` 等语义前缀，避免双重否定 | `isSaving`、`canRetry` |
| NAM-05 | React Hook | `use` 前缀，遵守 Hook 调用规则 | `useRecordList` |
| NAM-06 | 普通目录和模块文件 | kebab-case；同类文件保持一致 | `record-service.js`、`record-list/` |
| NAM-07 | 数据表、列 | snake_case；约束和索引名称表达用途 | `saved_records`、`owner_id` |
| NAM-08 | 测试文件 | 被测模块名加 `.test.js` 或 `.test.jsx` | `record-service.test.js` |

1. 必须避免拼音、无意义缩写及 `data1`、`tmp2`、`doSomething` 等模糊命名。循环局部索引 `i`、`j` 和团队术语表中的 `id`、`url` 等通用缩写可使用。
2. 函数名必须描述动作，查询用 `get`、`list`、`find`，写入用 `create`、`update`、`save`；名称须与实际副作用一致。
3. 时间、大小、金额等数值必须标识单位或通过类型明确单位；例如 `timeoutMs`。业务枚举集中定义，避免散落的状态字符串和无说明数字。
4. `const` 不等于常量命名：运行时值 `const currentUser = ...` 仍用 lowerCamelCase。
5. 外部 API、数据库字段及框架保留名称遵循其契约，在适配层转换；不得为满足风格私自修改公共字段。

```js
const MODEL_TIMEOUT_MS = 30_000; // 团队示例值，实际值由配置确定。
const canSave = isAuthenticated && hasSaveConsent;

async function findRecordById(recordId, accessScope) {
  return recordRepository.findById(recordId, accessScope);
}
```

## 3. 格式与编码习惯（FMT）

1. **FMT-01 必须**使用 UTF-8、LF、二空格缩进，文件末尾保留换行，清理行尾空白。Markdown 有意使用的换行空格除外。
2. **FMT-02 必须**由共享格式化配置统一引号、分号和换行；本版选用 JS 单引号、分号、格式化目标行宽 100。长 URL、字符串等由格式化器处理，不强制拆断语义内容。
3. **FMT-03 必须**使用 `const`，仅在需要重新赋值时使用 `let`，禁止新增 `var`；默认使用严格相等比较，特殊类型转换须明确说明。
4. **FMT-04 必须**为条件和循环添加花括号；优先使用提前返回降低嵌套。禁止依赖隐式赋值完成条件判断。
5. **FMT-05 必须**使用 ESM `import/export`；工具要求 CommonJS 时使用明确的 `.cjs` 配置边界。导入按外部依赖、内部共享模块、当前模块、样式分组；禁止循环依赖和未使用导入。
6. **FMT-06 建议**函数有效代码超过 50 行、源文件超过 300 行或控制流嵌套超过 3 层时检查是否可拆分。这是评审触发线，不为凑行数机械拆分；生成代码、数据表和声明式配置除外。

## 4. 注释与接口文档（DOC）

1. **DOC-01 必须**注释解释业务原因、边界、约束和取舍，不逐行复述代码。代码变更时同步更新注释。
2. **DOC-02 必须**为公共服务函数、共享契约、复杂算法及具有副作用的工具补充 JSDoc：用途、参数结构、返回值、可能的错误及副作用。局部简单函数可依靠清晰命名。
3. **DOC-03 必须**对权限过滤、取消判定、幂等键作用域、隐私清理等关键约束说明“为什么需要”，并关联需求或设计文档。
4. **DOC-04 必须**让 TODO 可追踪：`TODO(owner, issue): 待办及完成条件`。不得用 TODO 代替当前发布必需的鉴权、异常处理和测试。
5. **DOC-05 必须**通过 Git 保存历史。废弃代码可先隔离并说明原因；需要删除文件时，仍须遵守第 10 节的用户授权要求。
6. **DOC-06 必须**在 README 中提供环境版本、安装、启动、配置变量、数据库迁移和测试命令；示例一律使用合成数据及占位密钥。

 * @param {{ownerId: string, entry: string}} accessScope - 服务端确定的访问范围。

## 5. 文件组织与依赖方向（STR）

以下为职责布局示例，不要求立即迁移现有目录；项目现有 `prototype/` 可承担前端目录职责。路径调整应单独评审。

```text
project/
├── prototype/src/
│   ├── app/                  # 应用入口和路由
│   ├── features/             # 按业务拆分的页面、组件、Hook
│   ├── components/           # 跨业务展示组件
│   └── api/                  # HTTP 客户端和接口适配
├── backend/src/
│   ├── routes/               # HTTP 参数、响应与路由
│   ├── middleware/           # 鉴权、请求标识、错误处理
│   ├── services/             # 用例编排和业务校验
│   ├── repositories/         # 数据访问
│   ├── adapters/             # 模型、检索及外部服务
│   └── db/migrations/        # 数据库迁移
├── shared/                   # 无密钥、无服务端副作用的契约
├── electron/                 # 主进程、preload 和 IPC 边界
├── docs/                     # 接口、设计、规范、验证记录
└── tests/                    # 跨模块集成和端到端测试
```

- **STR-01 必须**遵守依赖方向：界面 → API 客户端 → 路由 → 服务 → 仓储/外部适配器。路由不承载核心业务，组件不直接访问数据库或模型供应商。
- **STR-02 必须**按业务聚合代码，限制公共工具范围。不得将大量无关逻辑放入 `utils.js`，不得用全局可变对象共享用户状态。
- **STR-03 必须**使共享 Schema 可被前后端安全引用，禁止将服务端密钥、数据库连接或 Node 专属模块带入前端产物。
- **STR-04 必须**分离配置和业务逻辑；启动时校验必要配置，缺少关键项时给出不含秘密的诊断并终止启动。
- **STR-05 建议**一个文件只承担一类明确职责；公共 API 保持精简，跨业务模块经明确导出边界调用。

## 6. 数据、接口与业务边界（DAT）

### 6.1 输入与接口契约

1. **DAT-01 必须**由服务端验证所有外部输入。前端校验用于交互反馈，不代替服务端鉴权、格式和业务检查。
2. **DAT-02 必须**前后端复用 Zod 等共享 HTTP Schema。写入契约拒绝未知字段；查询参数明确转换和默认值。内部仓储 DTO 与 HTTP DTO 分离。
3. **DAT-03 必须**从可信会话取得身份，客户端传入的 `ownerId`、角色和入口声明不能直接作为授权依据。对象读取和修改须校验归属及入口范围。
4. **DAT-04 必须**按已确认业务规则定义空值、长度、时区及枚举。若长度约定为 Unicode 码点，使用 `Array.from(text).length`；不得与 UTF-16 长度或用户感知字符数混用。密码不擅自 `trim` 或 Unicode 规范化。
5. **DAT-05 必须**用明确契约表达时间：瞬时时间使用含时区的 ISO 8601，日期字段使用约定的日期格式；禁止依赖机器本地时区推断业务含义。

### 6.2 数据库与并发

1. **DAT-06 必须**使用参数化 SQL，禁止字符串拼接用户输入；动态表名、列名及排序字段使用固定白名单。
2. **DAT-07 必须**对需要共同成功的写入使用事务，使用同一 `pg` 连接执行 `BEGIN/COMMIT/ROLLBACK`，并在 `finally` 中释放连接。
3. **DAT-08 必须**结合唯一约束和业务校验实现幂等：同一作用域内同一请求标识及同载荷返回既有结果，不同载荷返回冲突。不能仅凭内存变量保证幂等。
4. **DAT-09 必须**对并发修改检查 `expectedVersion`；不匹配返回冲突，禁止静默覆盖更新。数据库约束作为一致性的最终防线。
5. **DAT-10 必须**将迁移纳入版本控制；已在共享环境执行的迁移不直接改写，使用后续迁移修正。执行前记录目标环境、备份及恢复方案。

## 7. 异步、React 与资源生命周期（ASY）

1. **ASY-01 必须**处理所有 Promise 的成功和失败；禁止无说明的未等待异步调用及空 `catch`。
2. **ASY-02 必须**为外部服务配置超时、取消和并发上限。仅对可安全重试的临时故障有限重试，并使用退避；非幂等写入无幂等保护时禁止自动重试。
3. **ASY-03 必须**在换号、退出、切换入口、重来或结束任务时失效旧请求。请求发出时捕获当前身份、会话、入口及活动代次，回填前重新核对。仅使用 `AbortController` 不足以保证无旧结果回填。
4. **ASY-04 必须**通过显式状态表示加载、成功、失败、暂停和取消，避免多个布尔量形成互相矛盾的状态；轮询进入终态后停止。
5. **ASY-05 必须**遵守 React Hook 规则，正确声明依赖；列表使用稳定业务 ID 作为 key，可重排列表不得使用数组索引。
6. **ASY-06 必须**清理 Effect 注册的计时器、监听器、订阅、网络请求、动画和音频资源。禁止在渲染期间执行持久化和网络副作用。

## 8. 异常处理与日志（ERR）

### 8.1 处理原则

- **ERR-01 必须**区分输入错误、未认证、权限拒绝、资源不存在、版本冲突、限流、外部服务故障及未知错误。业务失败不得伪装成空列表或成功响应。
- **ERR-02 必须**在能恢复、补偿或转换错误语义的层处理；无法处理则向上抛出。服务端边界统一转换响应，避免各层反复记录同一异常。
- **ERR-03 必须**保留内部诊断链用于受控排障；响应不得包含堆栈、SQL、凭据、内部路径或供应商原始异常。进入日志前也须清洗异常信息。
- **ERR-04 必须**在失败和取消路径释放资源、回滚事务并恢复界面可操作状态。未知错误默认返回安全的通用消息。

### 8.2 HTTP 错误约定

以下为团队基线；具体业务错误码与既有接口规范统一维护，禁止各模块自行扩展同义错误。

| 状态码 | 用途 | 客户端处理 |
| --- | --- | --- |
| 400 | 参数、格式或 Schema 校验失败 | 提示可修正字段 |
| 401 | 未登录或会话失效 | 清理失效身份状态，引导登录 |
| 403 | 已识别身份但不允许该操作 | 提示权限或用途许可要求 |
| 404 | 资源不存在，或按契约隐藏其存在性 | 提示无法访问，不泄漏归属信息 |
| 409 | 并发版本或幂等载荷冲突 | 提示刷新、比较并重新确认 |
| 429 | 请求频率超限 | 按服务端等待提示处理 |
| 503 | 外部依赖或服务暂不可用 | 明确失败，允许安全重试 |
| 500 | 未知内部错误 | 通用提示及请求标识 |

成功响应采用 `{ data, meta: { requestId } }`，失败响应采用 `{ error: { code, message }, meta: { requestId } }`。字段级提示只能包含已确认允许返回的信息。

### 8.3 日志

1. **ERR-05 必须**使用结构化日志，包含事件名、经校验的请求标识、状态、耗时及必要的脱敏标识。`debug/info/warn/error` 分别用于调试、正常事件、可恢复异常及需要处理的失败。
2. **ERR-06 必须**禁止记录密码、Cookie、令牌、真实聊天正文、完整模型提示和响应、SQL 参数及含敏感值的 URL。测试和开发日志同样遵守。
3. **ERR-07 必须**区分应用日志、审计记录和测试证据，明确访问权限与保留期限。日志及监控采集不能绕过业务隐私规则。

## 9. 安全与项目专有约束（SEC）

以下是本项目材料中的业务边界及其工程化落实，不作为 CSDN 论坛原文引用。

1. **SEC-01 必须**通过环境变量或受控密钥系统注入秘密；前端可访问的变量只放公开配置。禁止提交 `.env`、真实用户材料和凭据；`.env.example` 仅含占位值。
2. **SEC-02 必须**按现有认证基线实施密码哈希、会话撤销、Cookie 属性和 CSRF/Origin 校验；演示账号和客户端本地状态不能代替正式认证。
3. **SEC-03 必须**区分模型外发许可与主动保存许可；许可具有明确用途和生命周期。不得因用户允许一次调用就默认允许持久保存或后续其他用途。
4. **SEC-04 必须**使文字销毁功能（REQ14）使用私有状态、本地资源和独立生命周期，不接入通用 API、仓储、模型或遥测。完成、跳过、异常和退出时清理输入、引用、拆字节点及相关资源。
5. **SEC-05 必须**验证销毁路径的网络、存储和遥测行为，报告具体检查范围。清理 JS 引用不等于可证明的物理内存擦除，不得对用户作超出验证能力的承诺。
6. **SEC-06 必须**限制 Electron 渲染进程权限，启用上下文隔离，通过 preload 暴露最小 IPC 白名单，验证消息来源和参数；禁止向网页暴露任意命令执行及任意文件访问能力。
7. **SEC-07 必须**将外部检索内容和模型输出视为不可信输入，验证工具调用参数与输出结构；展示 HTML、Markdown 和外链前进行安全处理。模型输出不能直接获得数据库、系统或用户身份权限。
8. **SEC-08 必须**评审新增依赖的用途、许可证及已知风险，保持锁文件同步；依赖告警须有处理结论。敏感信息误提交时先吊销或轮换秘密，后续历史清理遵守用户授权要求。

## 10. Git、评审与变更管理（VCS）

### 10.1 分支与提交

1. **VCS-01 必须**从团队确认的集成分支创建短期任务分支。本工作区新增分支采用 `codex/<任务短名>`；受保护分支通过 PR 合并。
2. **VCS-02 必须**保持提交单一目的；禁止将大规模格式化、依赖升级和业务修复混为一个难以审查的提交。
3. **VCS-03 必须**采用 Conventional Commits 的消息结构；本团队约定使用 `feat`、`fix`、`docs`、`refactor`、`test`、`style`、`build`、`ci`、`chore`、`perf`。其中附加类型是团队选择，不是该标准全部强制要求。参见 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)。

```text
fix(records): prevent stale results after logout

Record the session generation and reject results from an expired scope.

Refs: #<真实Issue编号>
```

占位编号在实际提交前必须替换。破坏兼容的变更使用 `!` 或 `BREAKING CHANGE`，写明迁移方式。中文或英文提交说明均可，含义须明确。

4. **VCS-04 必须**提交源码、迁移、测试及锁文件；排除 `node_modules/`、临时日志、真实数据和可重新生成的运行产物。需要交付的构建物经单独发布流程管理。
5. **VCS-05 必须**禁止强推共享分支、覆盖他人未合并修改和使用破坏性命令丢弃未知工作。冲突解决后重新执行受影响检查。
6. **VCS-06 必须**在删除项目文件前取得用户明确允许，授权范围应覆盖拟删除路径。包括重命名、移动、清理和历史操作中会删除的文件；未获允许时保留文件并记录待清理项。审批记录关联 Issue 或 PR。

### 10.2 PR 与发布

- **VCS-07 必须**由至少一名非作者评审；作者不能仅凭自测自行认定验收完成。涉及认证、隐私、数据库和 Electron 权限的修改须有相关模块负责人参与。
- **VCS-08 必须**在 PR 写清问题与触发条件、最终行为、关联需求、验证结果、未覆盖范围及兼容性；界面修改附关键状态截图，数据库变更附迁移和恢复说明。
- **VCS-09 必须**使发布版本可定位到提交，记录环境、迁移、配置变化、验证与回退方式。修订本规范同样经 PR 留下版本和采纳记录。

## 11. AI 辅助开发（AID）

| 角色 | 可执行任务 | 人工必须承担的责任 |
| --- | --- | --- |
| AI 设计师 | 检查需求、接口和状态遗漏，提出方案 | 确认需求、取舍、权限和隐私边界 |
| AI 程序员 | 根据既定契约生成代码、重构建议和文档 | 阅读差异，检查依赖及来源，运行相关验证 |
| AI 测试员 | 提出边界用例、生成合成数据及测试草稿 | 确认预期结果，真实执行并解释失败 |

1. **AID-01 必须**给 AI 提供目标、技术栈、契约、禁止事项及验收条件；使用最小必要上下文，禁止输入真实凭据和私人正文。
2. **AID-02 必须**将 AI 产出视为待审草稿；禁止直接采纳无法解释的代码、虚构 API、未核验依赖或来源不明的大段复制内容。
3. **AID-03 必须**记录日期、工具/模型（可取得时）、任务、输入约束、采纳范围、人工修改、测试命令及结果、关联提交。不能把生成测试脚本写成测试通过。
4. **AID-04 必须**由提交者承担最终质量责任，AI 不能替代非作者评审；冲刺日志如实披露贡献和失败，不虚构节省工时、会议或运行证据。

## 12. 测试、自动检查与完成定义（QA）

### 12.1 测试要求

1. **QA-01 必须**按风险选择验证：核心业务规则写单元测试；认证、SQL 和事务做集成测试；关键跨端流程做端到端或有记录的人工验收。纯文案和格式调整无需机械新增测试。
2. **QA-02 必须**覆盖受影响功能的正常、边界和失败路径，优先验证：未登录、越权、账号/入口隔离、许可缺失、过期结果、取消、超时、重复提交、版本冲突及回滚。
3. **QA-03 必须**使用隔离环境和合成数据；不能默认连接生产库或在测试中清理用户文件。测试清理需要删除文件时先按 VCS-06 取得允许。
4. **QA-04 必须**区分 Mock、PGlite、真实 PostgreSQL、真实模型调用及端到端验证；通过某一层不能代替其他层的完成证明。
5. **QA-05 必须**让结果可复现：记录提交版本、环境、命令、结果和限制。不得通过跳过失败测试、弱化断言、忽略退出码或伪造报告获得通过状态。

### 12.2 检查职责

| 检查 | 执行位置 | 阻断条件 |
| --- | --- | --- |
| 编码与格式 | EditorConfig、Prettier | 变更文件不符合共享格式 |
| 静态检查 | ESLint，React Hooks 检查 | 未定义变量、未使用导入、Hook 规则错误等 |
| 自动测试 | 各模块实际配置的测试命令 | 相关测试失败或缺少关键验证 |
| 构建 | 前端及实际交付模块 | 构建失败 |
| 安全与契约 | 工具扫描及人工评审 | 未处理的越权、泄密、契约冲突 |
| 业务验收 | 非作者按 Issue 验收条件复核 | 预期行为未实现或证据不足 |

**当前状态说明：本次仅生成规范文档，未向业务仓库安装工具、修改配置、配置 CI 或运行业务测试。** 已读取的 Day1 快照中，后端有 `test`、`test:integration`，前端有 `build`；未见这两份 `package.json` 声明 `lint`、`format:check` 或前端测试命令。不能将下列目标命令描述为现已可用。

### 12.3 建议落地配置

团队可在独立配置 PR 中添加以下文件。EditorConfig 用于跨编辑器统一文本格式；Prettier 读取仓库配置以保持一致。配置机制参见 [EditorConfig 官方说明](https://editorconfig.org/) 与 [Prettier 配置文档](https://prettier.io/docs/configuration)。以下具体参数为团队选择。

`.editorconfig`：

```ini
root = true

[*]
charset = utf-8
end_of_line = lf
indent_style = space
indent_size = 2
insert_final_newline = true
trim_trailing_whitespace = true

[*.md]
trim_trailing_whitespace = false
```

`.prettierrc.json`：

```json
{
  "tabWidth": 2,
  "useTabs": false,
  "singleQuote": true,
  "semi": true,
  "printWidth": 100,
  "endOfLine": "lf"
}
```

配置 PR 必须锁定兼容的 ESLint、Prettier 和所需插件版本，配置浏览器/Node 环境、React Hooks 检查、忽略构建产物及生成代码。格式规则交给 Prettier，避免与 ESLint 重复冲突。建议在各包中合并以下 scripts，不覆盖原有条目：

```json
{
  "scripts": {
    "lint": "eslint . --max-warnings 0",
    "format:check": "prettier . --check"
  }
}
```

前置条件完成后，在各自包目录运行 `npm ci`、`npm run format:check`、`npm run lint`，再执行该包实际定义的测试和构建。后端执行 `npm test`；前端执行 `npm run build`；集成测试仅在隔离数据库和配置就绪后执行 `npm run test:integration`。前端测试工具应先选型并配置，不能通过 `--if-present` 隐藏缺失检查。

CI 必须使用相同脚本和锁文件；分支保护将必要检查列为必需项。首次引入时明确历史问题基线，先阻止新增问题，建立存量整改 Issue；完成建设后才可记为“自动检查已启用”。

### 12.4 PR 完成清单

- [ ] 需求或缺陷有真实 Issue，验收条件可执行。
- [ ] 命名、格式、注释和依赖方向符合本文。
- [ ] 输入、归属、用途许可和异步生命周期已检查。
- [ ] 失败路径、资源释放、事务及日志脱敏已检查。
- [ ] 相关检查实际执行，结果与验证层级如实记录。
- [ ] 契约、README、迁移和锁文件随变更同步。
- [ ] AI 贡献及人工验证已记录；不适用项注明原因。
- [ ] 至少一名非作者复核，未解决意见有明确结论。
- [ ] 涉及文件删除时已取得用户明确允许并留存范围。
