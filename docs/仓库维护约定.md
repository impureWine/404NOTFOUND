# 仓库维护约定

返回 [文档索引](README.md)。编码与评审细节见 [代码规范](代码规范.md)，职责及交付约束见 [团队协作规则](团队协作规则.md)。

## 文件放在哪里

| 内容 | 归属 |
| --- | --- |
| 项目简介、主要入口和最短启动方式 | 根目录 `README.md` |
| 团队共用规范与需求说明 | `docs/`，并登记到 `docs/README.md` |
| 团队 Alpha 计划、日志和总结 | `docs/alpha/` |
| 各成员第三次作业原稿 | 保留 `docs/第三次作业_姓名/` |
| 后端源码、迁移、测试及模块证据 | `backend/`，细节维护在其 README |
| 数据库专业设计、ER 图和基础 DDL | `database-design/` |
| React 演示源码 | `prototype/` |
| HTML 评审页面及资源 | `web-prototype/` |
| 离线单页演示 | `demo/` |
| PR 协作模板 | `.github/` |

根目录已有 PDF、PPTX 和个人清单继续保留原路径，通过索引分类。未来如需迁移，先明确路径、引用更新及删除授权，不自动搬动历史文件。

## 命名与版本

- 持续更新的团队规范使用稳定名称，例如 `代码规范.md`；版本、日期和采纳状态放在正文，通过 Git 追溯。
- 有明确时间归属的计划、会议和执行记录使用 `主题_YYYYMMDD.md`，避免“最终版2”“最新版”等不确定名称。
- 候选、计划、模板、已执行和已验收分别标记；不要根据文件名推断当前完成状态。
- 图像、附件与源文件随对应文档放置，并使用相对链接；不要复制同一份规范到各成员目录。

## 维护流程

1. 新增或修改文档时，同步更新最近的导航入口；重大交付同时更新 `docs/README.md`。
2. 链接以仓库实际存在的路径为准，保留路径大小写；GitHub 不支持本机磁盘路径。
3. 运行步骤与各包的 `package.json` 和锁文件一致。前端现用 npm 锁文件，后端现用 pnpm 锁文件；切换包管理器须单独评审并同步锁文件。
4. 在 PR 中说明改动目的、检查范围及限制。文档检查通过不能表述为应用测试通过。
5. 删除任何文件前必须取得用户明确允许；移动、重命名和清理中涉及原文件删除的操作同样适用。未获允许时保留原文件并记录建议。
