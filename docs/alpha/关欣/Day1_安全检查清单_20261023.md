## 3. 风险与缺口

分级依据：**高**＝阻塞业务接口开放；**中**＝现状可接受但接入即产生风险；**低**＝纵深防御与文档类问题。

### 高

#### H-01 无 HTTP 认证与会话中间件，也没有错误码到 HTTP 状态的统一映射

- **现象**：`createApp` 只注册了 `/health/live` 与 `/health/ready`，没有认证中间件、没有 `DomainError` 到 4xx/5xx 的转换、没有 `requestId` 注入。
- **位置**：`backend/src/app.js:1-24`（全文 24 行）
- **影响**：任何业务接口一旦按现有形态接上，会以"无身份"方式直接调用仓储；同时 `NotFoundError` 等错误将无法按契约映射为 404/409，界面无法区分"不存在"与"无权"。
- **建议**：接入层按 `AccessContext` 重建 `{accountId, entryPointId}`，与 `DomainError.code` 一一映射；在路由注册前完成，不得先在业务路由里各自处理。
- **责任**：李泉毅主责，关欣复核。
- **关联验收**：AT-SEC-04、AT-SEC-07。

#### H-02 契约把 `accountId` / `entryPointId` 作为入参，直接复用为 HTTP 契约即成"自报归属"

- **现象**：`scopeSchema` 是 `strictObject({ accountId, entryPointId })`，`recordCreateSchema` 在其上 `extend`。仓储把这两个字段视为**已认证输入**。
- **位置**：`backend/src/contracts/records.js:18-21`、`backend/src/contracts/records.js:25-27`
- **影响**：今天是安全的（没有 HTTP 层，客户端够不到）；一旦把这套 schema 直接当请求体契约，客户端就能指定记录归属，正是 AT-SEC-02 要防的形态。
- **今日已验部分**：严格契约会拒绝 `ownerId`、`entry` 这类未知字段（见用例 1），且省略 scope 会失败——但这只覆盖"字段名不同"的情况。
- **建议**：HTTP 层使用独立 DTO（不含归属字段），由中间件注入 scope 后再调用仓储；并把"客户端提交 accountId 会被忽略"写成一条 HTTP 级用例。
- **责任**：李泉毅、庄剀涵。
- **关联验收**：AT-SEC-02、P-24。

#### H-03 会话令牌承载与 CSRF 方案未定

- **现象**：`login_sessions` 只存 `token_digest`，签发与承载方式（HttpOnly Cookie 还是内存令牌）设计文档标为 D-05 待定；无 CSRF/Origin 校验代码。
- **位置**：`backend/src/repositories/identity-repository.js:84-138`；`database-design/sql/404notfound_postgresql.sql`（`login_sessions`）
- **影响**：承载方式直接决定是否需要 CSRF 防护。当前既无 Cookie 也无 CSRF 代码，属于"未评估"而非"已防护"。
- **建议**：Day 2 与李泉毅确定承载方式；若选 Cookie，必须同时给出 `SameSite`、`HttpOnly`、`Secure` 与 Origin/CSRF 校验，并补用例。
- **责任**：李泉毅、关欣。

### 中

| 编号 | 问题 | 位置 | 影响与建议 |
|---|---|---|---|
| M-01 | 密码摘要契约只校验长度 1～255，不校验算法格式；`passwordParameters` 为自由 `record` | `contracts/identity.js:17-18` | 若调用方误传明文，会被当作摘要原样入库，且 `algorithm` 列固定写 `ARGON2ID`，造成"看起来是哈希"的假象。建议契约增加 `argon2id$` 前缀或 `$argon2id$v=19$m=..` 结构校验，并在服务层统一生成摘要 |
| M-02 | 无结构化日志，也没有字段白名单 | `backend/src/server.js:13`（仅一行启动日志） | 现在没有正文泄漏，是因为**几乎不记日志**；一旦接入日志框架，正文、登录名、令牌极易进入日志。建议先落 ERR-05/06 白名单再补日志 |
| M-03 | 缺 helmet / CORS 策略 / 限流 / 请求 ID | `backend/src/app.js:1-24` | 已知风险，非缺陷；在对外暴露前补齐。限流阈值对应 D-02 待决 |
| M-04 | `getProfile(accountId)` 无入口约束，与权限矩阵 P-05"本人·当前入口"不一致 | `repositories/identity-repository.js:167-186` | 资料是账号级，跨入口可读。需与设计确认：要么改设计为"账号级可跨入口"，要么加 entry 校验。**这是设计与实现的真实分歧，需要一次明确决策** |
| M-05 | `revokeSession(sessionId)` 未校验账号归属 | `repositories/identity-repository.js:140-151` | `sessionId` 不出现在客户端契约中，风险低；仍建议加 `account_id` 条件作为纵深防御 |
| M-06 | 游标密钥 `randomBytes(32)` 为进程内生成 | `record-repository.js:18` | 多实例部署时互相拒绝对方游标，重启后旧游标全部失效。当前单实例可接受，需在部署设计里写明约束 |
| M-07 | 依赖审计依赖官方源；默认镜像源不提供 audit 接口 | 构建流程 | 本次用 `--registry=https://registry.npmjs.org` 才跑通。建议把该命令写入 CI，否则"无漏洞"无法复现 |

## 6. 对 Day 2 的三条具体要求

1. **接口开放前先上闸门**：`AccessContext` 中间件 + `DomainError → HTTP` 映射必须先于任何业务路由合入（H-01、H-02）。
2. **资料读取的入口语义要一次定死**：`getProfile` 是否跨入口可读，必须在设计与实现中给出同一个答案（M-04）。
3. **日志白名单先于日志框架**：不要先加 `pino` 再补脱敏，顺序反过来会留下无法追溯的历史日志（M-02）。
