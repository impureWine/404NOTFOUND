## 2. 逐条归因

### D2-03｜重复注册响应明确披露登录名已被使用

- **复现**：`POST /api/auth/register`，两次提交同一登录名（合成账号）。
- **实测**：第二次返回 `409`，`error.message` 直接为"登录名已被使用"。
- **根因**：
  - `backend/src/services/auth-service.js:136` —— `throw new ConflictError('登录名已被使用')`，冲突文案本身就是可枚举信号。
  - `backend/src/http/request.js:87` —— `message: status === 500 ? '服务内部错误' : error.message`，只要不是 500 就原样回显。
- **影响**：登录名存在性可被枚举；与 `SEC-01` 中"统一反馈、不泄露账号是否存在"的要求冲突。
- **建议**：冲突文案改为中性表述（例如"该登录名不可用"），并在 `errorHandler` 内对认证类错误统一替换，不依赖各调用点的字面量。
- **修复后验收**：`D2-03` 转绿，且 `D2-02`（同名被拒）保持绿。

### D2-17｜未知数据库异常把内部错误信息返回客户端

- **复现**：用例向数据访问层注入抛错，再请求受保护接口。
- **实测**：响应为 `503`，但 `message` 携带内部异常文本。
- **根因**：
  - `backend/src/http/request.js:82` —— `code = error instanceof DomainError ? error.code : error.code ?? 'SERVICE_UNAVAILABLE'`，未知异常被归为 503。
  - `backend/src/http/request.js:87` —— 回显条件以 `status === 500` 判断，503 落入回显分支。
- **影响**：堆栈之外的内部实现细节（表名、约束名、SQL 片段）可能经 `message` 外泄，违反 `ERR-03`。
- **建议**：把"是否可外显"改为显式白名单——只有已知 `DomainError.code` 才回显 `message`，其他一律通用文案；原始异常只进服务端日志。
- **修复后验收**：`D2-17` 转绿；`D2-18` 的请求标识仍保留。

### D2-18｜非法 JSON 应为 400 且有请求标识

- **复现**：向任意 JSON 接口 `POST` 一段非法 JSON（合成内容）。
- **实测**：返回 `503`（期望 `400`）。
- **根因**：
  - `backend/src/app.js:59` —— `app.use(express.json({ limit: '128kb', strict: true }))`，解析失败抛出 `SyntaxError`，带有 `type: 'entity.parse.failed'` 与 `status: 400`。
  - `backend/src/http/request.js:82` —— 错误映射只看 `error.code`，未识别 `error.status` 与 `error.type`，落到默认 `SERVICE_UNAVAILABLE` → 503。
- **影响**：客户端把"请求写错了"误判为"服务不可用"，会触发无意义重试；与接口契约 `INVALID_INPUT` 不一致。
- **建议**：在 `errorHandler` 增加请求体解析分支（`entity.parse.failed` → `INVALID_INPUT` / 400；`entity.too.large` → 413），并保留 `meta.requestId`。
- **修复后验收**：`D2-18` 转绿；补一条请求体超限返回 413 的用例。

### D2-20｜未认证请求不能触发内部模型适配器

- **复现**：不携带任何 Cookie，直接 `POST /internal/v1/model/generate`，使用计数替身适配器。
- **实测**：适配器被调用 **1 次**（期望 0 次）。
- **根因**：
  - `backend/src/app.js:72` —— 该路由在 `if (authService)` 分支之前注册，且路径前缀为 `/internal`，不经过 `app.js:107` 的 `app.use('/api', createSecurityMiddleware(...))`。
  - 路由体内只做 `modelAdapter.respond(request.body)`，没有身份、来源或用途许可校验。
- **影响**：任何能访问该端口的一方都能消耗模型配额，并可把任意文本送进模型上下文；与 Day 3 发现的 `H3-01`（`AI_PROCESS` 无落点）是同一处缺口的两个观察面。
- **建议**：内部入口加服务间鉴权（如共享密钥头 + 仅绑定回环地址），并在模型请求前校验用途许可；两者建议与 `H3-01` 合并设计。
- **修复后验收**：`D2-20` 转绿；`D3-06` 从"未实现"改判需要重新评估。

### D2-22｜获取认证上下文不应把 DESKTOP 会话重绑定为 WEB

- **复现**：构造 DESKTOP 入口的合法会话，读取 WEB 记录返回 404；再请求 `/api/auth/context` 换发 Cookie，用新 Cookie 读同一记录。
- **实测**：换发后返回 **200**（期望仍 404）。
- **根因**：
  - `backend/src/app.js:92` —— `await authService.createContext(existing?.accountId ?? null)`，换发时只传账号，丢弃了 `existing.entryPointId`。
  - `backend/src/services/auth-service.js:47-48` —— `createContext` 内固定调用 `ensureWebEntryPoint()`，入口维度被写死为 `WEB`。
- **影响**：同账号跨入口隔离被一条换发接口绕过，`SEC-09` 与权限矩阵 `P-13`/`P-09` 的口径失效。
- **建议**：`createContext(accountId, entryPointId)` 保留可信会话的入口并校验允许集合；换发不得改变入口维度；补一条"换发前后入口不变"的回归用例。
- **修复后验收**：`D2-22` 转绿；`D2-14`（服务端切换入口不能绕过）保持绿。

## 3. 三条共性根因

| # | 共性 | 涉及位置 | 说明 |
|---|---|---|---|
| 1 | 错误回显策略按 **HTTP 状态**判断，而不是按"是否允许外显" | `request.js:87` | 只要不是 500 就回显 `message`，导致 409/503 都可能泄露内部信息（D2-03、D2-17） |
| 2 | 第三方中间件的错误未纳入错误码映射 | `request.js:82`、`app.js:59` | `express.json` 的 `entity.parse.failed` 未被识别（D2-18） |
| 3 | 身份上下文的**入口维度**在换发路径上被写死 | `app.js:92`、`auth-service.js:47-48` | 换发丢入口、创建固定 WEB（D2-22） |

---

## 4. 建议的最小修复顺序

1. **D2-17 + D2-18**：同一文件 `request.js`，改动小、影响所有接口，先做。
2. **D2-22**：`auth-service.createContext` 增加入口参数，`app.js` 换发时透传；需同步补回归。
3. **D2-03**：文案策略调整，需与前端确认措辞，避免出现"改完不可枚举但用户看不懂"。
4. **D2-20**：需引入服务间鉴权方案，建议与 `H3-01` 一起设计，不要单独打补丁。
