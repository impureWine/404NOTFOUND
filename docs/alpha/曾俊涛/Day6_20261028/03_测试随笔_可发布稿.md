## 测试如何跟开发并行

Day 1 我建立启动、构建与测试基线；Day 2 对账号、资料、会话与授权做首批自动化；Day 3 扩展陪伴、训练、查询的成功及异常路径；Day 4 聚焦游客与登录、主动保存、A/B 隔离、两步清除、模型许可及文字销毁；Day 5 在候选主线上集中回归；Day 6 固定新主线 SHA，重跑全部基础用例、跨层验收、浏览器与发布配置检查。每次保留源码版本、命令、退出码和原始结果。代码单测的“接口按实现工作”与用户从正式界面达成目标是两个不同结论。

我把场景分为四层：①合同与单元测试；②HTTP＋隔离数据库跨层测试；③真实浏览器页面与网络；④发布配置及真实环境。PGlite 是隔离 PostgreSQL WASM，用来验证迁移和 SQL 行为；它不能替代正式 PostgreSQL 16 的角色权限、备份恢复、网络和性能验收。模型探针使用计数替身，没有向真实模型发送测试内容。

## 我们发现了什么

最大的教训是：**全量自动化变成 123 条全绿，发布判定仍是 BLOCKED**。新增 3 条测试刻意断言当前缺陷签名：错误 Origin、缺 CSRF、无 `AI_PROCESS` 许可仍触发模型替身；同账号跨入口仍能读／取消 AI 任务；失效会话写请求返回 403。它们的“通过”是复现稳定，不是安全目标满足。修复者应将断言改成拒绝行为，再在新 SHA 上复测。

我另外用 13 项跨层门槛检查用户价值。记录详情虽然 HTTP 200，返回的却是不可展示的密文字段，用户无法回看自己主动保存的正文；内部模型入口虽然有登录要求，却没有通过受测 Origin、CSRF 与用途许可边界。这两项足以阻止“可发布”结论。真实账号 UI＋QA API 的 A/B 数据隔离通过，也只说明这一条受测路径，不覆盖完整页面保存与历史闭环。

## 项目评述、限制与下一步

团队已经形成认证、记录、许可、检索、AI 适配及前端演示的可复跑基础；开发期自动化回归和截图证据能让修复前后比较清楚。当前短板集中在跨模块交接：记录解密响应与页面接线、模型入口统一鉴权、AI 任务入口作用域、文字销毁运行时取证，以及正式 PG16／HTTPS／密钥与部署验证。原型界面和作者自查应继续保留，但标清模拟与真实链路。

本次本机包标识 `0.1.0-rc.local.20261028+19ad7eb`，用于复现与答辩的技术证据，不是正式上线版本。下一轮先修 P0 和两项纵向红灯，接上正式保存／历史／销毁页面，再用新 SHA 重跑浏览器闭环；授权环境到位后补数据库迁移与恢复、真实模型／来源、HTTPS 和故障回滚。若明天仍有未关闭项，应按事实交接，不把计划燃尽曲线当实际完成。
