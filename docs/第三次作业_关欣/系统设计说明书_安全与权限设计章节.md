### 4.1.2 范围与明确不做的事

本章覆盖 SRS 中 REQ07（安全与隐私）及其散落在 REQ03、REQ05、REQ06、REQ10、REQ12、REQ14、REQ16、REQ17 的安全子条款，共 14 条安全要求（SEC-01～SEC-14，见表 4-2）。

以下内容属于本版范围之外，安全设计不得为其预留界面、接口或管理入口：密码找回与重置、账号注销、公开主页与社交、后台管理员与运营端、自动跨端同步、烦恼漂流瓶、系统级无痕承诺（操作系统、输入法、外部录屏不在产品控制范围）。若评审追问「为什么不设计管理员权限」，回答口径为：本版无管理端需求，RBAC 的管理角色不适用，详见 4.4.1。

### 4.1.3 安全域与信任边界

系统按 SRS 第 2.2.1 节的分层（接入层、应用服务层、能力适配层、数据层）划分安全域。安全域之间只通过受控接口传递最小数据，图 4-1 用边界线标出信任关系，是本项目「系统安全性」答辩页的主图。

![图4-1 安全域与信任边界](图4-1_安全信任边界_v1.0.png)

图 4-1 的读法与五条跨越规则：

1. **客户端域不可信**。Web 页面、桌宠客户端、微信入口中的任何字段（`ownerId`、`entry`、`recordId`、`version`、`confirmed`）都按不可信输入处理，服务端一律重建身份上下文（`AccessContext`），不采用客户端自报归属。
2. **接入层只做两件事**：建立可信 `AccessContext`（入口 + 可选登录会话）与限流；不做业务判定，也不能把请求转成「无身份」的业务调用。
3. **应用服务域是唯一的授权判定点**。`SecurityPolicy` 与 `ConsentGrant` 的校验在此完成；仓储、模型、检索都是被调用方，不得反向决定权限。
4. **外部能力域降权**。模型与检索供应商只接收白名单载荷，不持有凭据、账号标识与其他入口历史；其返回内容一律按不可信数据处理。
5. **文字销毁位于客户端域内的独立视图**，与其余所有域无连线（图 4-1 中以虚线框与「无正文通路」标注）。这是 REQ14 的结构性保证，不是运行时开关。

## 4.3 身份认证设计

### 4.3.1 凭据模型与摘要

认证的目标是证明「当前操作者是账号本人」，它只解决身份问题，不代替保存授权、外发授权与同步授权（SRS 2.5 约束三条）。因此本设计把三件事分开：登录会话证明身份，业务会话承载当前任务，`ConsentGrant` 决定内容能否落库或外发。

登录名与密码的输入契约沿用 SRS 表 9：`LoginName` 3～64 字符、标准化（去首尾空白、统一大小写折叠）后唯一；`PasswordInput` 8～128 字符，仅在请求期间存在于内存。密码不以任何形式落库、落日志或进入模型上下文，持久化的只有不可逆摘要与盐。

摘要算法作为技术决策（表 4-22 的 D-01），本节只固定不可让步的约束：使用抗 GPU 的慢哈希（Argon2id、scrypt、bcrypt 之一）、每账号独立随机盐、参数记录在配置文件而非代码、摘要计算与比较使用常量时间比较。禁止明文、可逆加密、MD5、SHA-1、无盐哈希，也不允许为了「便于排查」保存密码或其可解密副本。

表4-3 凭据相关字段与存储策略

| 数据项 | 输入约束 | 存储位置与形式 | 禁止事项 |
|---|---|---|---|
| 登录名 | 3～64 字符，标准化后唯一 | 身份表，明文（仅用于识别，不用于鉴权） | 用昵称代替登录名鉴权 |
| 密码 | 8～128 字符，临时输入 | 不存储；仅存摘要与盐 | 明文、可逆加密、日志、模型上下文、错误消息回显 |
| 令牌原文 | 服务端签发 | 只在签发响应与客户端安全容器中短暂存在 | 进 URL、Referer、日志、崩溃上报、埋点 |
| 令牌摘要 | — | 登录会话表 `tokenDigest` | 以原文形式持久化 |
| 密码修改记录 | — | 不单独建表，仅体现在会话撤销时间 | 记录新旧密码或历史密码明文 |

### 4.3.2 注册、登录、改密、退出的鉴权时序

四条链路共享同一原则：先校验再产生副作用；副作用要么全部生效，要么全部不生效；失败信息统一而不泄露账号是否存在。

注册（对应 REQ16、AT-16）：校验必填项与两次密码一致 → 校验登录名标准化后唯一 → 在单一事务中创建账号、资料、凭据、账号偏好四件套 → 返回登录态。任一步失败不留下部分账号；唯一约束冲突以 `INVALID_INPUT` 统一返回「该登录名不可用」，不区分「已存在」与「格式非法」以外的内部原因。

登录：标准化登录名 → 校验失败计数与限流（4.3.4）→ 取出摘要并做常量时间比较 → 校验返回目标是否在白名单 PageKey 内 → 建立登录会话（写入 `tokenDigest`、`expiresAt`、`device`、`entry`）→ 签发令牌。比较失败与「账号不存在」返回同一提示；比较成功但账号处于不可登录状态时，同样走统一提示，避免枚举。

修改密码：要求当前会话有效 → 校验当前密码 → 新密码强度与两次一致 → 在事务内替换摘要 → 撤销该账号全部旧会话（含当前会话）→ 要求重新登录。撤销他人会话是这条链路的核心价值，验收时必须检查旧令牌立即失效，而不是「下次登录才失效」。

退出：撤销当前会话令牌摘要 → 递增业务会话代次使进行中的请求失效（4.8.5）→ 清除界面内私密内容与端侧内存桶 → 停止训练、浮层输入与音频。退出不等于删除已保存记录（SRS 表 10），文档与 PPT 必须区分这两个概念。

### 4.3.3 会话状态与撤销

表4-4 登录会话状态与行为

| 状态 | 触发 | 服务端行为 | 界面行为 | 后续私密请求结果 |
|---|---|---|---|---|
| 有效 | 登录成功且未过期 | 接受 AccessContext | 显示当前账号 | 按权限矩阵放行 |
| 过期 | 超过 expiresAt | 拒绝，不回退为游客 | 停止私密访问内容展示，引导重新登录 | AUTH_REQUIRED |
| 已撤销（退出） | 用户退出 | 摘要失效 | 清除私密内容与任务 | AUTH_REQUIRED |
| 已撤销（改密） | 修改密码成功 | 该账号全部会话失效 | 强制重新登录 | AUTH_REQUIRED |
| 已撤销（并发上限） | 同账号新会话超过上限（阈值待确认） | 撤销最早会话 | 提示已在其他设备登录 | AUTH_REQUIRED |
| 已切换账号 | A 退出后登录 B | A 的请求代次失效 | 不显示 A 的任何内容与迟到回复 | 按 B 的权限判定 |

会话与入口的关系：一个登录会话对应一个 `entry`（WEB、DESKTOP、WECHAT）。同账号在不同入口各自登录、各自隔离，不共享同一令牌；「同账号其他入口」在权限矩阵中按「拒绝读取业务记录」处理（SRS 表 5、REQ06）。这条设计既是隐私要求，也让多端调试不会互相污染数据。

| 防护对象 | 措施 | 超限表现 | 状态 |

## 4.4 权限设计

### 4.4.1 权限模型选择：为什么不用 RBAC

课程参考资料给出了 RBAC（用户—角色—权限—组）方案。本项目评估后采用「主体—对象—入口—用途」的属性化校验，理由有三条，答辩时可直接引用：

1. 本版没有管理端。RBAC 的价值主要在多角色、多岗位的功能授权（谁能进哪个功能）。本项目只有一个自然人身份「本人」，角色映射退化后只剩一个角色，无法表达真正的差异。
2. 真正需要判定的是**对象级**关系。「这条记录是不是我的、是不是我这个入口保存的、是不是已经过期或被撤销」属于数据归属判定，只能落到对象上，不能落到角色上。
3. 真正需要判定的是**用途级**关系。同一份正文，本人可以看、可以存，但是否允许发往模型要单独授权，且授权绑定对象版本。用途授权无法用角色—权限映射表达。

因此设计采用 ACL 与属性校验的组合：对象上携带 `ownerId` 与 `entry`，授权上携带 `purpose`、`resourceId`、`resourceVersion`。同时保留一条可扩展性说明——若后续版本引入运营或审核角色，应在服务端增加角色层并复用同一校验点，不修改现有对象归属字段。这样既不虚增本版功能，也不堵死演进路径。

### 4.4.2 五要素校验与执行点

每一次私密操作都必须同时满足五个条件，缺一即拒绝（SRS 3.2.2）。图 4-2 描述校验流水线，拒绝时统一由 `SecurityPolicy` 返回 `ACCESS_DENIED` 或 `AUTH_REQUIRED`，并且**不区分「不存在」与「无权」向用户呈现的信息量**，仅在服务端内部区分以便排错。

表4-6 鉴权执行点与职责

| 执行点 | 职责 | 不做什么 |
|---|---|---|
| 接入层 | 由可信通道建立 AccessContext（entry + 可选登录会话）；限流；尺寸限制 | 不解析业务载荷决定归属；不代客户端指定 ownerId |
| 应用服务 | 五要素校验；调用 SecurityPolicy 与 ConsentGrant；组织事务 | 不把权限判定下推给客户端或数据库注释 |
| 仓储 | 所有查询强制带 ownerId + entry 条件；更新/删除带 expectedVersion | 不提供「按编号查询」的无归属接口；不接受应用层传入的已信任标记 |
| 能力适配（模型、检索） | 只接收白名单载荷，返回结果不带权限 | 不判断记录归属，不持有凭据 |

三层都要校验的理由是纵深防御：应用服务漏判时，仓储的条件约束仍会拦住越权读写；仓储条件写错时，应用服务的判定还能兜住。验收目标是「界面、请求载荷、直接构造的请求」三种路径都拿不到他人记录。

### 4.4.4 用途授权

保存授权回答「这条内容能不能落库」，用途授权回答「这条已保存内容能不能发给外部能力处理」。两者都按对象与版本绑定，均可撤销，且都不构成全局授权。

表4-8 用途授权（ConsentGrant）规则

| 用途 | 适用对象 | 校验条件 | 失效条件 | 撤销方式 |
|---|---|---|---|---|
| SAVE | 五类保存对象（CONVERSATION、EMOTION、WORRY_OBJECT、REHEARSAL_DRAFT、DEPOSIT） | 登录有效 + 当前入口 + 载荷类型匹配 + 用户本次明确提交 | 提交完成后即消耗，不跨次复用 | 用户取消保存 |
| AI_PROCESS（LISTEN） | 当前会话中用户选定的文本 | 登录有效 + 文本为用户本次输入或显式选中 + 版本匹配 | 会话结束、切换任务、取消、代次递增 | 用户停止或删除消息 |
| AI_PROCESS（ORGANIZE） | 已保存的烦恼物件正文 | 登录有效 + 物件属于本人当前入口 + resourceVersion 匹配当前版本 | 正文更新（版本变化）、清除记录 | 用户撤销授权 |
| AI_PROCESS（REHEARSE） | 当前排练轮次中的用户表达 | 登录有效 + 属于当前轮次 + 用户显式开始模拟 | 重来（新轮次）、退出、取消 | 用户重来或结束 |
| SEARCH_CONTEXT | 用户为查询选定的必要上下文 | 登录有效 + 用户逐项选择 + 不含其他入口历史 | 查询请求结束 | 用户取消携带 |

明确三条禁止：不得用「登录成功」推导出任何 AI 用途授权；不得把一次授权扩展到其他记录（`resourceId` 必须精确）；不得在正文更新后复用旧版本授权（`resourceVersion` 必须匹配，SRS 3.6.4）。

表4-9 越权威胁与设计对策

| 威胁 | 本项目中的具体形态 | 设计对策 | 验证用例 |

### 4.4.6 破坏性操作与清除确认

清除、延期、改密是三类不可直观回退的操作，统一采用「服务端签发确认 + 客户端回传 + 服务端核验」的模式，而不是信任前端的确认弹窗。

`ClearConfirmation` 携带记录编号、记录版本、所有者、入口与过期时间，默认 `confirmed=false`，签发后短时有效且只能使用一次。服务端核验签发事实、版本与范围后再执行；执行时正文副本、房间外观关联与活动引用在同一事务内处理，任一步失败整体回滚并返回 `SERVICE_UNAVAILABLE`，不出现「提示清除成功但记录还在」。

更新与清除都必须带 `expectedVersion`：一致才写入并递增版本，不一致返回 `CONFLICT` 并保留编辑内容。

### 4.5.3 日志、埋点与崩溃上报

SRS 要求「日志只记录必要的非正文状态和耗时，故障定位不以收集私密正文为前提」。只有列出的字段允许进入日志，其余一律不采集。

表4-12 日志字段白名单

| 允许记录 | 用途 | 禁止记录 |
|---|---|---|
| requestId、服务方法名、状态码、错误码 | 定位失败环节 | 任何正文、标题、描述、事件文本 |
| 入口类型、客户端版本、平台 | 区分入口问题 | 登录名、昵称、邮箱类信息 |
| 记录编号（UUID）、记录类型、版本号 | 定位数据问题 | 情绪词、强度、寄存正文、排练表达 |

三条配套规则：① 错误消息统一走 `DomainError(code, safeMessage)`，`safeMessage` 由服务端提供，不含敏感字段；② 埋点与崩溃上报共用同一白名单，不因为「第三方 SDK 默认采集」而例外；③ 排错需要样本时，使用合成数据复现，不开启正文采集开关。

### 4.5.4 端侧存储与传输

传输：全链路 HTTPS，证书校验开启；凭据不放入 URL、查询串或 Referer；微信入口只做跳转，聊天窗口内不输入密码（SRS 表 3）。

端侧存储：业务正文与令牌不写入 `localStorage` 等可长期读取的持久化存储；界面偏好等非敏感设置可以本地保存，但不得与正文混存。令牌承载方式（HttpOnly Cookie 或内存短时令牌）待与前端确认（D-05）。文字销毁不使用任何持久化缓存、不生成自动草稿、不进入会话 restore 机制。

### 4.5.5 密钥与配置管理

数据库口令、令牌签名密钥、第三方模型与检索的 API Key 一律通过环境变量或密钥管理服务注入，不入代码仓库、不入前端构建产物、不入日志、不入镜像明文。开发、测试、生产使用不同密钥。任何示例代码与截图在提交前必须做密钥扫描，仓库开启最小权限与分支保护。

### 4.6.2 检索内容不可信与提示注入

检索是把不可信的外部文本引入系统的唯一入口，因此按「数据永远不是指令」建模。设计上把进入模型的内容分三层：系统规则（服务端固定，用户与外部文本都不可修改）、用户输入（可影响任务内容，不可影响权限）、外部文本（只作为被引用的事实材料，不具指令权）。三层用结构化边界分隔，外部文本不得拼接进系统规则区域。

表4-15 检索与外部文本的安全控制

| 控制点 | 措施 | 失败表现 |
|---|---|---|
| 来源链接 | SafeUrl 校验：只接受 http 与 https，拒绝 javascript、data、超长与畸形链接；展示域名与来源标题 | 链接不可点击，标注来源不可用 |
| 摘要与来源绑定 | 每条事实摘要至少关联一个来源；无来源不作为确定结论呈现 | 显示「依据不足」而非编造 |
| 来源质量 | CURRENT、STALE、UNKNOWN 分别呈现，冲突单独说明 | 显示时间不明或来源冲突状态 |
| 指令注入 | 外部文本不进入指令区；能力侧无权限，越权请求必然失败 | 忽略注入内容，正常返回事实结果 |
| 上下文膨胀 | 来源数量与文本长度上限（阈值待确认） | 截断并提示，不静默扩大上下文 |
| 失败状态 | 无结果、超时、来源过期、来源冲突分别反馈 | 与服务失败区分，不混为「没有内容」 |

表4-16 危机表达处理档位
