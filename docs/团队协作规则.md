# 404烦恼未找到——团队协作与交付规则

**适用对象：** 全体 8 名成员，包含组长和各交付物整合负责人。

**适用范围：** 本次“原型设计与需求分析”作业。任务责任沿用《第二次团队作业_任务分工与贡献表.md》，本规则约束执行和交付方式，不新增开发任务。

**执行说明：** 本规则作为统一执行文本，由组长发送给全员。各成员须在团队沟通群确认“已阅读并按规则执行”；未确认不视为已经同意。规则调整须留存变更记录并通知全员，不得在提交前临时改变他人的验收要求。

## 一、任务与责任

1. 每项任务必须明确负责人、交付位置、截止时间和验收条件。协作者须列明具体协助内容，不能用“共同负责”替代责任划分。
2. 成员按既定分工交付；跨成员、跨章节的变更须先与受影响负责人同步，并由张王昊记录确认。未达成一致的变更不得直接并入最终稿。
3. 本次只交付作业要求的博客、原型、需求规格说明书、两份答辩 PPT 和两份评审表；不得擅自增加开发、部署等任务作为本次必须完成的内容。
4. 负责人不仅提交初稿，还须完成评审意见修订、版本交接和最终核对。整合负责人不能替代各成员对自己内容的责任。

## 二、任务同步与延期

1. 全员在同一个任务表记录状态：**未开始 → 进行中 → 待评审 → 待修订／已验收**。仅负责人完成自查时，状态仍为“待评审”。
3. 预计无法按时交付时，须在发现风险当天说明剩余工作、影响范围、需要的协助及新的预计时间，由组长与受影响成员协调调整。
4. 沟通群用于讨论，任务表用于记录结论。涉及范围、责任、期限和验收的决定均须写入任务表。

**统一任务记录：**

| 任务编号 | 任务及交付物 | 负责人／协作者 | 截止时间 | 验收条件 | 状态 | 文件或链接 | 阻塞及处理结论 |
| -------- | ------------ | ------------- | -------- | -------- | ---- | ---------- | -------------- |
| T-01 | 填写具体任务 | 姓名及协助内容 | 月日 时分 | 可检查的完成条件 | 未开始 | 相对路径或共享链接 | 无／具体说明 |

## 三、内容编写范式

1. 全部交付物统一使用团队名称“404烦恼未找到”；项目名称、入口名称、功能名称和术语以团队确认的需求规格说明书为准。
2. 当前功能名称与编号统一沿用《404烦恼未找到_项目功能总览与新增需求_v0.3.md》的 REQ01～REQ17，覆盖账号与个人中心、陪伴与沟通、记录与整理、压力缓解、信息支持、基础与多端六个模块；需求编号统一按最新总览连续排列，子功能不重复计数。术语首次出现须说明含义；缩写首次出现须给出全称。后续功能版本经确认后同步更新相关材料。
3. 需求按“项目目标 → 用户场景 → 功能要求 → 输入输出 → 验收标准”分层描述，不将设计设想写成已经实现的事实。
4. 每项功能使用唯一需求编号，如 `REQ01`。类图说明、原型页面、验收标准及 PPT 中引用该功能时须沿用同一编号，新增或变更编号由张王昊维护。
5. 所有功能按以下模板提交，不适用项须说明原因，不得留下含义不清的“待完善”。

```text
需求编号与名称：
用户与使用场景：谁在什么情况下需要完成什么任务
前置条件：开始操作前需要满足的条件
输入：输入内容、格式及必要限制
正常流程：按用户操作顺序描述系统行为
输出：结果内容、呈现方式及状态
异常流程：无结果、超时、无效输入等情况下的行为
涉及原型：页面编号或链接
验收标准：给定……，当……，应当……；写出可观察的判断条件
```

6. 场景、类图、原型和验收标准须对应同一组功能。出现名称、流程或范围不一致时，先确认需求，再同步修改相关材料。
7. 引用的资料、图片和图表须标明来源；真实用户反馈须有可核对、已脱敏的记录。不得编造访谈、评审意见、实验结果或完成记录。使用 AI 辅助生成的内容由提交成员核查并承担责任。

## 四、格式与交付文件

| 交付物 | 全员统一遵守的要求 |
| ------ | ------------------ |
| 博客 | 使用 Markdown；保留作业信息表和目录；按作业要求设置标题；分工表使用“学号、工作内容、贡献度”三列，比例合计 100%；正文中的交付链接对应最终版本。 |
| 需求规格说明书 | 使用同一 Word 模板和标题样式；正文默认宋体小四、1.5 倍行距；标题采用自动编号，目录自动生成；图表连续编号并注明名称；各成员不单独修改全局字体、页边距和样式。由曾俊涛统一排版。 |
| 界面原型 | 使用同一原型项目及组件样式；页面有唯一编号；交互入口、跳转和退出路径明确；演示数据统一，示例内容标明为示例；分享链接具备评审所需访问权限。由郭昱祺维护整体风格。 |
| 两份答辩 PPT | 使用同一 16:9 模板、配色和字体；每页围绕一个主题；原型截图与类图清晰可辨；功能名称、编号和数据与说明书一致；提交可编辑源文件，导出 PDF 后检查错位和缺字。 |
| 两份评审表 | 使用腾讯共享文档；包含小组名称、项目名称、评审内容、评审建议及各组名称和排名；评审意见依据实际展示填写，不提前虚构；链接具有规定的访问权限。 |

**文件命名：** `404烦恼未找到_交付物名称_v版本号.扩展名`，例如 `404烦恼未找到_需求规格说明书_v1.0.docx`。不使用“最终版2”“最新版”等无法区分版本的名称。

提交给整合负责人时，同时提供可编辑源文件、所需导出文件和版本说明；原型与共享评审表提供链接及版本／更新时间。版本说明至少写明修改人、时间、修改内容和受影响的需求编号。

## 五、版本协作与冲突处理

1. GitHub 仓库统一管理日常协作、源码和文档版本，已确认版本作为团队交接依据；聊天附件只用于交接，不能自动替代已确认版本。课程要求的需求规格说明书 Word 和两份答辩 PPT 仍上传华为云仓库，在博客给出对应链接；课程文件提交时间以华为云记录为准，推荐同时提交 PDF。
2. Markdown 等文本文件使用个人分支提交，由对应整合负责人核对后合并；提交说明写明交付物与修改目的，例如 `docs: 补充REQ03查询验收标准`。
3. Word、PPT 等文件明确当前编辑人，实行同一文件同一时段由一人编辑；其他成员提交修改建议或独立章节素材，不能同时覆盖整合稿。共享原型按页面划分编辑责任。
4. 修改他人负责的内容前须同步。发生内容争议时，按“课程要求 → 已确认需求 → 用户证据”的顺序核对，由相关负责人讨论，张王昊记录处理结论。
5. 禁止未经相关成员同意覆盖其未合并内容、强制推送覆盖共享历史或重置他人工作。冲突解决后须检查双方有效内容是否保留。
6. **删除任何项目文件前，必须获得张王昊（本工作区提出删除约束的用户）的明确允许。** 申请须列明路径、原因和是否已有备份；其他成员批准、将文件移入回收站或已有备份均不能替代该允许。未获允许时保留原文件并标记旧版本。

## 六、评审与完成标准

1. 每项交付至少由一名非作者成员复核。作者完成自查、复核人检查并留下结论后，才能标记“已验收”。
2. 自查与复核至少覆盖：要求是否完整、描述是否准确、关联材料是否一致、格式是否统一、文件是否可打开、链接是否可访问。
3. 发现问题须记录“所在位置、具体问题、修改要求、负责人、修订期限”；不得只写“优化一下”。修订后由原复核人确认。
4. 各整合负责人分别核对说明书、原型和两份 PPT；曾俊涛核对导出文件、仓库版本及链接；张王昊核对博客要求与整体交付清单。
5. 答辩负责人须使用最终演示文件完整试讲一次，检查原型访问、翻页、图表清晰度及材料一致性；内容负责人须能解释自己提交的部分。

**统一交接说明：**

```text
任务编号／交付物：
提交成员与版本：
文件路径或共享链接：
本次完成内容及修改点：
自查结果：
尚未解决的问题与影响：无／具体说明
复核人及结论：待评审／通过／需修订（附问题）
```

## 七、节点与提交

1. 全员遵守任务表中确认的内部截止时间。**首稿至少在课程截止时间前 48 小时交接，最终稿至少提前 24 小时完成评审与整合，提交和链接检查至少提前 6 小时完成。** 组长将上述节点换算成明确时间写入任务表；课程时间调整时同步更新。
2. 内部截止与课程截止分别记录。博客需要审核，不能将“已发布”直接视为“已提交作业”；最终须检查作业页面提交记录及华为云仓库文件。
3. 进入最终稿阶段后，范围或核心流程变更须列出对说明书、原型、PPT 和验收标准的影响，由相关负责人及组长确认后同步修订；错别字、排版和失效链接可按原定责任直接修正并记录。

## 八、贡献认定与规则执行

1. 分工表中的比例是计划工作量，最终贡献以实际承担的任务、验收通过的产物、有效修订和协作记录为依据，不直接按代码行数、聊天条数或在线时长认定。
2. 临时接手、协助和返工须记录原任务及实际内容，同一成果不能由多人各自计为完整独立贡献。贡献表须与最终任务分工保持一致，总和为 100%。
3. 张王昊汇总贡献表，各成员核对涉及自己的事实；有争议时由相关成员提供记录，并由至少一名无直接利益关系的成员参与复核。组长本人适用相同程序。
4. 首次违反流程时记录问题、明确修正方式与期限；再次出现相同问题或已经影响交付时，由组长协调调整任务和复核安排，并如实记录实际完成情况。不得临时引入未约定的罚款或任意扣减贡献比例。
5. 合理求助、主动上报风险以及经确认的任务调整，不单独作为违规或扣减贡献的理由。任何成员均可指出规则执行问题，讨论针对事实和交付，不进行人身评价。
