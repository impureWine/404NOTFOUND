7. 记录 LLM 不能替代的人工判断。

# 案例一：混合意图与模式切换

## 1. 设计问题

用户可能在一句话中同时表达情绪和事实问题，例如：

> 我最近找工作很焦虑，你能顺便帮我查一下今年国考什么时候报名吗？

系统既不能忽略用户的焦虑，也不能在没有检索来源时直接回答报名时间。需要确定陪伴与查询之间如何切换，以及是否必须让用户确认。

## 2. 提示词整理稿（项目名已统一）

```text
我正在设计一个名为“404NOTFOUND”的智能体。它有陪伴交流、短时自助练习和带来源的信息查询三种模式。用户可能说：“我最近找工作很焦虑，你能顺便帮我查一下今年国考什么时候报名吗？”

请提出三种可实现的处理方案，分别比较：
1. 用户是否清楚当前回答类型；
2. 是否保留用户控制权；
3. 事实回答能否追溯来源；
4. 前后端实现复杂度。

限制：系统不能进行心理诊断，不能在无可靠来源时编造事实，不能在用户未确认时自动开始练习。先给候选方案，不要替项目组直接作最终决定。
```

## 3. LLM 候选方案整理

LLM 给出了三种候选方案：

### 方案 A：一次性完成陪伴和查询

先用一句话回应用户的焦虑，然后立即搜索报名时间，并把结果与来源一起返回。交互步骤少，但系统可能在没有明确提示的情况下改变回答类型，也不清楚用户此刻更希望被倾听还是获得信息。

### 方案 B：先回应情绪，再询问是否切换

先简短承接用户表达，再提供“继续聊聊”和“查询报名时间”两个选项。用户确认查询后，系统只提取事实问题进入搜索流程，并显示来源。该方案多一次交互，但模式边界、用户控制和来源要求更清楚。

### 方案 C：并列显示两个独立区域

在同一页面同时显示陪伴回应和查询卡片，并允许用户继续任一方向。信息完整，但页面和后端需要同时维护两个任务，状态、加载和失败反馈更复杂，移动端也可能显得拥挤。

LLM 倾向方案 B，并建议保留用户原始输入，避免取消切换后重新输入。

## 4. 方案审查记录（原稿整理）

| LLM 建议 | 处理结果 | 人工判断 |
|---|---|---|
| 一次完成陪伴和查询 | 拒绝作为默认流程 | 可能形成静默切换，也可能在搜索失败时把事实与陪伴语言混在一起 |
| 先简短回应，再让用户选择 | 采纳 | 符合 FR-M03、FR-M04 的一次确认要求 |
| 同时显示两个独立区域 | 暂不纳入 MVP | 实现和状态管理复杂，超出首版核心流程 |
| 取消切换后保留原输入 | 采纳 | 减少重复输入，符合 FR-M05 的失败/取消回退原则 |
| 自动识别后直接修改后台模式 | 拒绝 | 意图识别只是建议，不能代替用户确认 |

## 5. 最终决策

采用“简短承接＋一次确认＋单路径执行”的方案：

1. 系统识别到混合意图后保持当前模式；
2. 简短承接用户当前表达；
3. 提供“继续聊”和“查询并显示来源”两个方向；
4. 进入 `WAITING_CONFIRMATION`；
5. 用户确认后才由服务端修改模式；
6. 切换查询时只携带事实问题和必要条件；
7. 用户取消后恢复陪伴模式，不重复弹出相同确认。

## 6. 对设计成果的影响

- `01-AI设计说明.md`：增加“混合意图”和状态转换规则；
- `02-智能体编排与时序图.md`：形成“混合意图与查询切换时序图”；
- `03-模型适配契约.md`：将 `OFFER_SEARCH` 定义为建议动作，而非直接切换动作；
- `05-AI模块测试用例.md`：增加混合意图、确认和拒绝切换用例。

## 7. 人工判断不可替代之处

LLM 可以提出交互方案，但无法代表用户确认产品是否应该多一步操作，也不能决定课程 MVP 的复杂度范围。最终选择依据是团队既有需求中“系统不能无提示改变回答类型”的明确约束。

# 案例二：上下文最小化与隐私

## 1. 设计问题

陪伴对话需要一定历史才能理解“帮我安排一下”等省略表达，但每次发送全部历史会增加隐私、成本和干扰风险。需要确定上下文由哪些部分组成，以及切换到查询模式时携带什么。

## 2. 提示词整理稿（项目名已统一）

```text
请为“404NOTFOUND”智能体比较三种上下文方案：
A. 每次发送当前会话的全部历史；
B. 只发送最近若干轮对话；
C. 发送系统规则、当前模式、用户已确认目标、结构化历史摘要、最近四轮对话和当前输入。

请从回答连续性、隐私、调用成本、长对话稳定性、实现复杂度五方面比较。然后分析从陪伴模式切换到信息查询时，哪些内容应该保留，哪些内容不应发送给搜索服务。

限制：不能把模型推断的诊断、性格或心理状态写成事实；用户未选择长期留存时，不能假设可以永久保存历史。
```

## 3. LLM 候选方案整理

LLM 的主要比较如下：

| 方案 | 优点 | 风险 |
|---|---|---|
| A：全部历史 | 连续性最好，实现直观 | 隐私暴露面大、成本随对话增长、无关内容干扰、最终会超过上下文限制 |
| B：最近若干轮 | 成本低、实现简单 | 较早确认的目标可能丢失，用户使用代词或省略表达时容易误解 |
| C：摘要＋最近消息 | 在连续性、成本和隐私间较平衡 | 需要维护摘要准确性，并处理摘要更新和删除 |

LLM 建议采用方案 C，并提出将摘要保存为：用户目标、相关事实、用户选择和待确认问题。切换到查询时，只传递用户确认的事实问题、必要时间地点和筛选条件，不传递完整倾诉内容。

LLM 还建议“可以记录情绪标签以帮助模型保持语气一致”。

## 4. 方案审查记录（原稿整理）

| LLM 建议 | 处理结果 | 人工判断 |
|---|---|---|
| 全部历史作为默认上下文 | 拒绝 | 不符合最小必要原则，长对话成本和隐私风险持续增加 |
| 只保留最近消息 | 拒绝作为完整方案 | 可能丢失用户已确认目标和模式状态 |
| 结构化摘要＋最近四轮 | 调整后采纳 | “四轮”仅作为 MVP 默认值，后续通过测试调整 |
| 摘要包含用户目标、相关事实、选择和待确认问题 | 采纳 | 内容可核对，便于状态恢复 |
| 自动记录情绪标签 | 拒绝 | 容易把模型推断固化为事实，且可能构成额外敏感信息 |
| 查询时发送完整原始对话以便模型理解背景 | 拒绝 | 搜索只需要明确查询，不需要无关倾诉内容 |

## 5. 最终决策

修订后的上下文按以下内容组织：

```text
系统规则
+ 当前模式和会话状态
+ 用户已确认目标
+ 必要历史摘要
+ 经授权且与任务相关的长期记忆
+ 最近四轮相关对话
+ 当前输入
+ 当前任务工具结果
+ 输出约束
```

摘要只记录用户明确表达或确认的信息，不保存诊断、性格推断和未确认的情绪标签。切换到查询模式时重新构造最小查询上下文，而不是直接复制陪伴模式的提示词和对话历史。

“最近四轮”仅是设计阶段默认值。开发过程中应通过回归用例比较两轮、四轮及摘要方案，不把未经测试的值写成性能结论。

## 6. 对设计成果的影响

- `01-AI设计说明.md`：形成“上下文组成、长对话摘要、模式切换最小化、保存与清除”四部分；
- `03-模型适配契约.md`：新增 `confirmed_goal`、`summary`、`recent_messages` 和 `history_retention`；
- `05-AI模块测试用例.md`：新增长对话摘要、敏感内容不进入搜索、会话清除测试。

## 7. 人工判断不可替代之处

LLM 能列举隐私与成本风险，但无法替项目组取得用户授权，也无法决定哪些内容属于业务必需。特别是“情绪标签”虽然可能提升表面上的个性化，却会增加误判和敏感信息处理风险，因此被人工拒绝。

# 案例三：模型异常与课堂演示降级

## 1. 设计问题

课堂演示和真实使用都可能遇到模型超时、限流、空响应、格式错误或服务不可用。需要保证界面不无限加载、不丢失用户输入，并且在使用模拟数据时明确告知用户。

## 2. 提示词整理稿（项目名已统一）

```text
请为“404NOTFOUND”智能体设计模型异常处理方案，覆盖：接口超时、供应商限流、返回空内容、返回 JSON 格式错误、输出包含越界表述、搜索无结果和搜索来源冲突。

请为每类异常给出：检测方式、是否自动重试、最大尝试次数、用户提示和降级方案。项目需要进行课堂演示，可以准备模拟适配器，但模拟结果不能伪装成真实模型或真实搜索结果。不能无限重试，也不能丢失用户原始输入。
```

## 3. LLM 候选方案整理

LLM 建议：

- 超时和空响应可自动重试一次；
- 限流采用退避，不立即连续提交；
- JSON 格式错误可使用更严格的结构提示重试一次；
- 越界内容不直接展示，改用安全模板或返回可恢复错误；
- 搜索无结果时不让模型依据记忆补写答案；
- 来源冲突时展示冲突点和时间，不作确定性结论；
- 外部模型不可用时可调用备用模型；
- 课堂演示可用模拟适配器，但响应中必须有 `mock=true`，页面明确显示“模拟结果”。

LLM 最初还建议“为了提高成功率，可以在超时后重试三次，并在后台继续等待结果”。

## 4. 方案审查记录（原稿整理）

| LLM 建议 | 处理结果 | 人工判断 |
|---|---|---|
| 超时和空响应重试一次 | 采纳为默认起点 | 在恢复能力和等待时间间较平衡，实际参数仍需测试 |
| 超时后重试三次并后台等待 | 拒绝 | 可能导致用户长时间等待、重复计费和重复结果，不适合 MVP |
| 限流后立即重复提交 | 拒绝 | 可能加剧限流，应退避或提示稍后重试 |
| 格式错误后使用严格结构重试一次 | 采纳 | 仍失败时拒绝异常结果，不直接展示半成品 |
| 搜索无结果时让模型基于常识补全 | 拒绝 | 违背来源可追溯要求，容易产生幻觉 |
| 模拟适配器标记 `mock=true` | 采纳 | 既保证课堂流程可演示，又不伪造真实服务结果 |
| 向用户显示供应商原始报错 | 拒绝 | 信息难以理解，并可能暴露内部实现和敏感信息 |

## 5. 最终决策

1. 模型调用默认超时 10 秒，最多自动重试一次；该值由实现测试后配置化调整。
2. 同一自动重试沿用 `request_id`，避免重复记录为两个逻辑任务。
3. 外部服务仍失败时优先使用已配置的备用适配器；没有备用时返回结构化错误。
4. 课堂演示可以启用 `MockModelAdapter`，但响应和界面必须明确显示模拟标记。
5. 无论何种失败，前端都保留用户输入，并提供重新尝试、返回原模式或结束会话。
6. 搜索无结果时不调用模型生成确定性事实答案；来源冲突时显示冲突和日期。

## 6. 对设计成果的影响

- `02-智能体编排与时序图.md`：形成模型异常与降级时序图；
- `03-模型适配契约.md`：形成统一错误结构、错误码、重试和幂等规则；
- `05-AI模块测试用例.md`：加入超时、限流、空输出、格式错误、无来源和来源冲突用例。

## 7. 人工判断不可替代之处

模型可以给出技术选项，但重试次数、等待时间和是否启用模拟器属于产品体验与成本决策，必须结合课程演示环境和实际接口测试决定。本文将相关值标记为设计默认值，避免把未经测量的参数写成最终承诺。

## 2026-10-22 修订：三个示例如何落实本次要求

本轮用户明确提出：接入智谱或通义千问的 LLM API，自行完成 Agent 编排与记忆，并说明与直接使用豆包、GPT 类产品的区别。对已有三个案例据此进行了以下细化，均是设计修订，未宣称已经执行代码或完成效果测试。

| 示例 | 继续驱动 LLM 分析的具体问题 | 本轮分析与修订结论 | 可检查的成果 |

| 一：混合意图与编排 | 如果多个任务节点共享一个 API 模型，怎样避免模型直接改模式？ | 一个主编排器控制有限任务节点；意图只是候选；用户确认后由程序调工具与更新状态；不需要分别训练多个 Agent 模型 | 01 第 1.1、5.1.1 节；02 总图与查询时序；06 问题一、二 |

案例二中，按用户隔离读取、冲突更新、删除传播是应用代码和数据管理的工作，不能只依靠一句“请记住用户偏好”。案例三中，异常处理也不能只让模型回复“请稍后再试”，还必须由程序停止重试、保留输入并避免重复写入。这些落点同时构成项目应用层工作量的说明。
